# nordwind-landscape

The curated **system-of-systems model** of the (fictional) Nordwind Retail estate —
the enterprise half of the article *"Your architecture is already documented — in
your code"*.

## How it works

1. Each service repo owns its own **architecture slice**, regenerated by CI on every
   push to `main` with [`crayon-c4`](https://www.npmjs.com/package/crayon-c4):
   [nordwind-storefront](https://github.com/cristinamudura/nordwind-storefront) (Next.js),
   [nordwind-orders](https://github.com/cristinamudura/nordwind-orders) (Java / Maven),
   [nordwind-payments](https://github.com/cristinamudura/nordwind-payments) (.NET).
2. A scheduled workflow here pulls those slices into `slices/` and opens a **review
   PR** when anything changed upstream. Extraction is automatic; *acceptance* is a
   human act.
3. `landscape/nordwind-landscape.json` is the curated estate model: the three
   systems, the externals (Stripe, PostgreSQL, Kafka) and the **cross-system
   relationships** — the part no single repo can know, because repo A only knows it
   calls *a* payments API, not that it is Team B's `payment-service`.

## The rules this demo lives by

- The source of truth is a **model, not a picture** — diagrams are projections.
- The model has a **published, versioned schema**; every slice is validated in CI.
- Elements carry **stable IDs**, so a re-run recognizes "same container, new name".
- A re-run **never silently discards manual curation**; removals are opt-in.
- Machines own structure; **humans own meaning**.
